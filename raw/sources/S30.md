# Prefill/Decode Disaggregation — DGX Spark + Mac Studio

**Heterogeneous P/D inference**: fast GPU prefill on NVIDIA DGX Spark cluster, high-throughput decode on Apple Silicon. KV cache transferred via ZMQ over 10GbE.

**Current status (2026-03-04)**:
- The main P/D decode slowdown was an **MLX slow-path** triggered by **KV cache dtype mismatch during injection**.
- Forcing bf16 injection (`--inject-dtype bfloat16`, or auto-detect) restores native MLX decode throughput.
- With that fix, P/D is the fastest end-to-end mode for `ctx=256..8192` (200 generated tokens) in our setup.
- At longer contexts (16K/32K), **DGX-only** can win on total time and has much lower TTFT; Mac-only can OOM at 32K.

## Key Finding (Post-bf16 Inject Fix)

P/D disaggregation delivers the **lowest total time from 256→8192 context** (tested) by combining:
- DGX's fast prefill (low TTFT, scales well with context)
- Mac's native decode throughput (bf16 KV inject fast-path restored)

**Router recommendation**
- If your production workload is mostly `ctx <= 8192`: **Always P/D** (Mac-only only as fallback for network/P/D failures)
- If you must support **16K+ contexts**:
  - `ctx <= 8192`: **P/D**
  - `ctx ≈ 16384`: **near the crossover** (depends on whether you optimize TTFT vs total time / stream tok/s; measure for your output lengths)
  - `ctx >= 32000`: **DGX-only** (Mac-only can OOM; P/D prefill+xfer overhead dominates)
  - `8192 < ctx < 16384`: measure
- Micro-optimization (short output, 32 generated tokens): `ctx <= 32` Mac-only, `ctx > 32` P/D (difference is ~10–40ms at ctx=16/32)

## Why P/D Works

```
DGX Spark Cluster (TP=2)          Mac Studio M4 Max 128GB
┌─────────────────────────┐       ┌─────────────────────────┐
│ Strength: Prefill        │       │ Strength: Decode         │
│ NVFP4: 1K–8K tok/s      │       │ MLX 4-bit: 13–24 tok/s  │
│ TP=2 × 200GbE fabric    │       │ 546 GB/s memory BW      │
│                         │       │                         │
│ Weakness: Decode         │       │ Weakness: Prefill        │
│ ~7–10 tok/s (GB10)      │       │ ~138–201 tok/s          │
└──────────┬──────────────┘       └──────────┬──────────────┘
           │  Shard 0 → ZMQ :9000            │
           ├─────────────────────────────────┤
           │  Shard 1 → ZMQ :9001            │
           └─────────────────────────────────┘
                    10GbE LAN, parallel
```

Each TP rank sends its KV shard directly to Mac — no inter-rank gather required.

## Architecture (v7 Multi-Shard)

```
Client ──POST /prefill──► vLLM TP=2 (dgxnode1 + dgxnode2)
                            │
                   ┌────────┴────────┐
              Rank 0 (node1)    Rank 1 (node2)
              save_kv_layer     save_kv_layer
              GPU→CPU (half)    GPU→CPU (half)
                   │                 │
              ZMQ PUSH :9000    ZMQ PUSH :9001
                   │                 │
                   └────────┬────────┘
                            │ 10GbE (parallel)
                            ▼
                   Mac Studio (MLX)
                   ZMQ PULL :9000 + :9001
                   Prealloc buffer + offset write (no concat)
                   Inject → MLX KVCache
                   Autoregressive decode
                            │
                            ▼
                   GET /results/{request_id}
```

## Methodology

- **Model**: Qwen3-32B — `nvidia/Qwen3-32B-NVFP4` (DGX), `mlx-community/Qwen3-32B-4bit` (Mac)
- **Generation**: fixed budget (`TOKENS=200` baseline, `TOKENS=32` router check), deterministic settings (temperature=0.0 / greedy)
- **Context files**: standardized prompts generated to target token counts (see `benchmarks/benchmark_runner.py`)
- **Tokenizer**: Same Qwen3 tokenizer across all modes
- **Warmup**: First run discarded; measurements from subsequent runs (`RUNS=3` baseline, `RUNS=5` short-output check)
- **Metrics**: total wall time (POST→complete), TTFT, P/D breakdown (prefill/xfer/decode), and throughput (`prefill_tok_s`, `decode_tok_s`)
- **vLLM**: `nvcr.io/nvidia/vllm:26.01-py3`, NVFP4 quantization, TP=1 standalone / TP=2 for P/D (see `scripts/start_vllm_pd.sh`)
- **MLX**: `mlx>=0.30` + `mlx-lm>=0.30`, 4-bit quantization (see `implementation/requirements-mac.txt`)
- **Hardware**: See below

## Limitations

| Issue | Impact | Status |
|-------|--------|--------|
| 10GbE network ceiling | ~1.2 GB/s practical; limits transfer at 32K+ | Hardware limit |
| Injected KV dtype mismatch | Wrong dtype can trigger MLX decode slow-path | Fixed via `--inject-dtype bfloat16` / auto-detect |
| Transport dtype | KV is serialized as FP16 for portability and cast to BF16 on Mac for fast-path decode | Acceptable for PoC |
| Different quantization | NVFP4 (DGX) vs 4-bit (Mac); not identical weights | Same model family, fair for throughput comparison |
| Chunked prefill disabled | vLLM connector bug with per-chunk KV overwrite | Waiting for upstream fix |
| Single request serial | No concurrent request support yet | Planned |

## Quick Start

### Mac Decode Server

```bash
cd implementation
python3 mac_decode_server.py \
  --model mlx-community/Qwen3-32B-4bit \
  --inject-dtype bfloat16 \
  --max-tokens 200 --port 8002 --tp-size 2
```

### DGX vLLM P/D Server (TP=2)

```bash
# See scripts/start_vllm_pd.sh for full setup
# Or manually:
# 1. Start containers on dgxnode1 + dgxnode2
# 2. Install pyzmq + msgpack, deploy zmq_kv_connector.py
# 3. Start Ray cluster (port 26379)
# 4. Launch vllm_pd_server.py --model nvidia/Qwen3-32B-NVFP4 --tp-size 2 \
#       --mac-endpoint tcp://<mac_ip>:9000 --mac-http-url http://<mac_ip>:8002
```
