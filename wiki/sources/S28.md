## Findings

- A setup guide for **data-parallel LoRA fine-tuning across 2+ Macs** using stock `mlx_lm lora` under `mlx.launch`, with gradients synchronized by `mx.distributed.all_sum()`. No new training code is claimed; the contribution is configuration.
- Requirements stated: macOS 26.2+, MLX 0.30+, 32–128 GB per node, a direct Thunderbolt 4 or 5 cable, full mesh for N nodes.
- Backend table (source-reported): ring over TCP about 500 µs latency and about 10 Gbps effective; JACCL RDMA 5–9 µs and 50–60 Gbps but with provider bugs listed (protection-domain leak after ~60 transfers, 100 memory-region cap per host, queue-pair degradation after ~23 minutes idle). The guide recommends the ring backend.
- Source-reported scaling: "2 nodes ≈ 1.8–1.9x single-node throughput" for same-model LoRA; ring sync overhead "~5–10%". An example log shows 623.8 tokens/s on Qwen3-8B-4bit, batch 2, grad checkpointing.
- Operational findings: long validation pauses drop the ring TCP connection; use `networksetup` rather than `ifconfig`; a Thunderbolt kernel panic workaround on macOS 26.6.1; a dual-plane layout with SSH over Wi-Fi and data over Thunderbolt.

## Limitations of this reading

README only. The "first published guide" claim is the authors'. The numbers are from unspecified nodes described only as 128 GB each.

## What this source blocks

- "Distributed LoRA fine-tuning across Macs with MLX" is already done with stock tooling. MacReduce's local-SGD trainer connecting Macs over IP does not add a capability over `mlx.launch` plus `average_gradients`; it only changes the synchronization schedule, which [S04](S04.md)–[S08](S08.md) already study.
- It documents that Thunderbolt RDMA is operationally fragile on current macOS, so any plan that **assumes** JACCL must budget for failure and must not be the project's critical path.
