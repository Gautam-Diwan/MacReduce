## Findings

- The maintainer states this is "a research project, not a production framework", a proof of concept for ANE training via `_ANEClient` and `_ANECompiler` private APIs, with utilization "~5-9% of peak" and many element-wise operations falling back to CPU.
- Reported training throughput on M4: Stories110M (109M params) 91 ms/step; Qwen3-0.6B (596M) 412 ms/step. Forward and backward dx passes run on ANE; **dW gradients run on CPU** (Accelerate cblas) and the Adam update runs on CPU. So "ANE training" here is a hybrid ANE/CPU pipeline.
- The README explicitly lists a **"GPU↔ANE zero-copy pipeline via shared IOSurface (GPU prefill → ANE decode)"** and a file `gpu_prefill_ane_decode.m`. A reported M4 table at seq=256 gives Stories110M GPU prefill 6.7 ms, ANE decode 1.9 ms; Qwen3-0.6B 9.7 ms and 2.3 ms. This is the file that supports the IOSurface claim; [S11](S11.md) (training README) does not contain it.
- INT8 W8A8 is reported at 1.88x throughput over FP16 on a convolution microbenchmark; peak ANE throughput reported as 18.6 TOPS FP16 and 35.1 TOPS INT8 on M4.
- Limitations stated by the source: ANE ignores `attn_mask` in SDPA so causal masking is split across ANE/CPU; a ~119 compile limit per process forces `exec()` restarts; fp16 gradient underflow requires loss scaling; single-input constraint. Requires macOS 15+, tested on M4; private APIs may break with any macOS update.

## Limitations of this reading

README only; no code audit; no independent timing. The decode number is a single-token figure for small models, not a throughput claim for a chat-size model. Nothing in the file describes a multi-machine or scheduler component.

## What this source blocks

- "First ANE training" and "first GPU-prefill/ANE-decode handoff on one Mac" are not available as claims. Both exist as documented prototypes.
- Any MacReduce ANE work must cite that dW and the optimizer live on the CPU in this reference, so "ANE training" comparisons need a stated boundary.
