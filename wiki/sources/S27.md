## Findings

- A Swift/Metal runtime for Gemma 4 26B-A4B (MoE) on a **16 GB M5, macOS 27 beta**. Experts are memory-mapped so the OS file cache is the expert cache; process RSS under 1 GB on short prompts.
- **The ANE does prefill only for routed experts**; the GPU unpacks the next 4 INT4 experts to FP16 while the ANE computes the previous 4 (reported 1.7x faster than GPU alone on long prompts; 8.8 s versus 15.3 s for a 3,015-token prompt, single runs). The ANE cannot unpack 4-bit weights, so GPU expansion is "the main limit on ANE speed".
- Speculative decoding uses a DFlash drafter entirely on the GPU. A `SpeculationPolicy` "decides each step, from measured timings and recent acceptance rates, how many tokens to draft and how many of those to verify, and drafts nothing when plain decoding would be faster." Source-reported decode: 51 tok/s without drafter, 99 tok/s with, on code prompts.
- Fault handling is explicit: `fail-closed` by default; `failover-metal` drops the ANE for the rest of the run and redoes the failed layer on GPU; tests require failover output to be bit-identical to GPU-only.
- Benchmarking method: A-B-B-A alternation in fresh processes, 95% confidence intervals, and a noise floor defined as the largest same-build difference.

## Limitations of this reading

README only. Hardware is M5 16 GB on a macOS 27 beta with private frameworks; MacReduce's M4 on macOS 26.5 is a different platform. The speculation policy is a per-step draft-length controller, not a device-placement controller, and its internals were not read.

## What this source blocks

- "ANE-assisted prefill for an MoE on a memory-constrained Mac" and "adaptive draft length from measured acceptance" exist. Neither is a free novelty claim.
- It supplies two conventions MacReduce should adopt rather than invent: no silent fallback with an explicit failover policy, and an A-B-B-A benchmark harness with a stated noise floor.
