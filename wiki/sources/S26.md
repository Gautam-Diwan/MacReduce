## Findings

- A Rust/Objective-C/Metal engine that runs Qwen3.5-2B (DeltaNet plus GQA) with **ANE batched prefill** via private `_ANEClient` APIs, **Metal GPU single-token decode** with custom shaders, and CPU NEON GEMV. The README says it is "not faster than llama.cpp (yet)" and is built for one architecture.
- Source-reported on an M5 for Qwen3.5-2B Q8_0: Metal decode 32 tok/s at about 15 W; CPU decode 23 tok/s at about 5 W; ANE prefill pp16 33 tok/s at about 3 W; fused ANE FFN 3.6 TFLOPS.
- Only DeltaNet layers use ANE prefill; full-attention layers are not yet batched on the ANE. Batch size 1 only.
- Under limitations: "No speculative decoding: Same-model speculation doesn't help (draft ~= verify speed). Needs separate tiny draft model." The README does not report an ANE-draft experiment.

## Limitations of this reading

README only; the hardware is an M5; the engine is single-model. No multi-machine component.

## What this source blocks

- Confirms a second independent ANE-prefill plus GPU-decode implementation exists (with [S23](S23.md), [S25](S25.md), [S27](S27.md)). The split itself is not open.
- Does not block, and in fact motivates, a measured answer to "is an ANE-resident draft model worth it", because the source says a separate draft model is needed and did not test one.
