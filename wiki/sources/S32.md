## Findings

- `mlx_lm.generate` exposes `--draft-model` ("A model to be used for speculative decoding.") and `--num-draft-tokens` (default 2 in `speculative_generate_step`).
- The implementation keeps a separate `draft_cache`, drafts `num_draft` tokens with `_step(draft_model, ...)`, verifies with one target `_step` over `num_draft + 1` positions, then **rewinds both caches with `trim_prompt_cache`**. It raises `ValueError("Speculative decoding requires a trimmable prompt cache ...")` when the cache type cannot be trimmed.
- The draft model is a second MLX model on the **same device** (GPU). There is no hook for an external or ANE-resident drafter; a draft produced elsewhere would have to be injected as tokens and the draft cache kept consistent by the caller.
- Acceptance is per-token comparison of the target's sample against the draft token; `from_draft` is reported per generated token.

## Limitations of this reading

Code reading only, no run. Behavior on MacReduce's MLX 0.32.4 was not checked against this `main` snapshot.

## What this source blocks

- Speculative decoding on MLX exists in the stock tool; building it is not a contribution. What the stock tool does not do is choose the drafter's engine, adapt draft length from measured acceptance (see [S27](S27.md) for a project that does), or route a draft across devices.
